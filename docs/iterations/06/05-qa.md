## 六、缺陷

### QA-03（低）：`backup` 中途失敗時，容器內的暫存備份檔沒有刪除

- **重現**（mock，QA 腳本 `scratchpad/qa6/leftover.py`）：

  | 情況 | 結果 | 是否刪除暫存檔 |
  |---|---|---|
  | `docker cp` 失敗 | rc=1，「❌ docker cp 失敗（Docker 是否已啟動？）：…」 | ❌ 沒有呼叫 `docker exec … rm` |
  | `RESTORE VERIFYONLY` 失敗 | rc=2，「❌ 連不上資料庫或備份失敗（請確認 Docker 與容器已啟動）：…verify failed」 | ❌ 同上 |

- **影響**：
  - 容器的 `/var/opt/mssql/data/` 會留下約 80 MB 的 `TwStock_YYYYMMDD_HHMMSS.bak`。
  - 訊息沒有說明這件事，使用者不知道要清。
  - 每失敗一次累積一份。
  - 另外，VERIFYONLY 失敗時的訊息是「連不上資料庫」，和真正的原因（驗證失敗）不符。
- **嚴重度低**：只在 Docker 或備份異常時發生，資料沒有風險，PM 的 9 項驗收都不受影響。
- **建議**：
  - 非 `--direct` 時，在 `finally` 裡刪除容器內的暫存檔；若刪除失敗，就印出它的路徑。
  - VERIFYONLY 失敗時另外給訊息，例如「備份檔驗證失敗」。

### QA-04（低）：`history --only holdings` 跑到今天時，跨境 ETF 的「今天」每次都被當成待抓

- **重現**：PG `logs/iter06_history_rerun.log`。11/04 21:32 執行 `history --start 2025-10-30 --only holdings`，結果是「待抓 1 天」（11/04，00411A、00988A），發出 2 次 `GetPCF`，回應都是「尚未公布」。
- **原因**：
  - `history` 判斷待抓時呼叫 `missing_keys` 沒有傳 `days`，不考慮 `delay`。這是第 5 輪就有的行為。
  - 跨境 ETF 今天的持股要明天傍晚才公布，所以只要 `--end` 是今天（預設值），每次都會白發 2 次請求。
  - 結尾的「無資料」也會列出今天。
- **影響**：
  - PM F6-1 #2 照字面執行時不是「0 請求」。
  - 設計 03 步驟 5、6 與 README 第 54 行的範例指令都沒有 `--end`，所以 PG 這次多發了 4 次請求。
  - 對資料正確性沒有影響：不會寫入，也不會記成 gap。
- **建議**：
  - `history` 對 `delay > 0` 的資料集，跳過「還沒到公布日」的日期（可以沿用 `missing_keys(…, days)`）。
  - 或在 README 的範例加上 `--end`。

## 七、不列缺陷的觀察

1. **00988A 的「尚未公布」用 ISO 字串 `0001-01-01T00:00:00`**（三-2）。目前判定正確，建議把這個格式加進 `test_iter06` 的反例。
2. **`etf_holding_gaps.created_at` 是容器時間（UTC）**，例如 13:31，台灣時間是 21:31。這和其他用 `GETDATE()` 預設值的表一致，只是查詢時要注意。
3. **網站 `status` 的「停在 MM/DD」可能指向 gap 日期**。例如 11/26 記成 A、11/27 又缺時，訊息會是「00988A持股停在 11/26」，但最後有明細的是 11/25。這只在異常時出現，而且 gap 日的清單本來就等同前一天，不影響判讀。
4. **`fetch_holdings` 的「今天」用的是電腦時鐘 `date.today()`**，不是 `tw_now()`。電腦設在台灣以外的時區時，B 的判定可能早一天或晚一天。使用者的電腦是台灣時區，沒有影響。
5. **設計已知、可接受**：
   - 臨時休市前一日的 B，當晚 22:00 後到生效日收集之前，會顯示異常。
   - 標記時，`history` 結尾的「無資料」會列出 gap 日期。
6. **PG `logs/iter06_backup.log` 沒有記到 rc**（zsh 的 `PIPESTATUS`）。不過 QA 用同一個指令另外實測 rc=0，可以佐證。
