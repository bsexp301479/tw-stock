## 二、成長圖獨立驗算（驗收 11、12、16）

- 方法（`logs/iter38_qa_graph_check.py`）：
  - 用 node 執行 `tlCpOut` 300 組隨機參數（P 0～10^11、M 0～10^9、r -99～100、n 1～50、殖利率 0～100、期初／期末、三種股利處理）。
  - QA 自己用 Decimal（80 位精度）重寫逐月複利，不呼叫 `test_iter38` 的 `_ref`、`check_graph`。
  - 比對：每條線每一點的座標（誤差 ≤ 0.006）、格線間距與縱軸上限、圖例和摘要表、對照線第 n 年。
- 結果：**300 組 0 差異**。
  - 金額在 2^53（約 9 × 10^15）以內時，圖例和另算值相差 ≤ 1 元，領出模式圖例 = 表格兩格相加。
  - 超過 10^14 的極大金額，JS 浮點運算 600 次的累積誤差約 10^-14（相對），照 PM 驗收 11 的規則用相對誤差 10^-12 比對，都通過；超過 2^53 時「兩格相加」無法精確，是浮點限制（見觀察 2）。

## 四、觀察（不算缺陷）

1. **375 寬座標說明尾字換行**：「第 0～20 年；縱軸 0～6,000,000 元，每格 2,000,000 元」在 375 寬換成 2 行，第二行只剩「元」。可讀、不溢出（設計第七節已記 n = 50 會換行）；要改可另排（例如縮短成「每格 200 萬元」）。
2. **極大金額超過 2^53**：例如 r = 100、n = 30 的領出模式，圖例「期末金額＋已領股利」51,380,982,897,644,930 和表格兩格相加差 6 元。這是 JS 浮點整數上限，第 34 輪的表格就有同樣限制；一般使用的金額不會遇到。
3. **質借結果表的值後面接一行說明**（例「7,397 元」下一行「÷365，四捨五入到元」）：是第 34 輪的版面設計，不在驗收 8（只管交易成本、複利）。
4. **320 寬交易成本當沖模式分段鈕 3 列**：設計已記，驗收只要求 375 ≤ 2 列（實測 2 列）。
5. 量測時發現：切換模擬色調或視窗寬度時，頁面會依網址重畫一次（`#/tools/cp`），量測要等畫面穩定；這是既有的路由行為，和本輪程式無關。
6. 主控台只有 1 筆 `ERR_CONNECTION_REFUSED`，是分頁在 8001 停止期間留下的；測試期間沒有 JavaScript 錯誤。
