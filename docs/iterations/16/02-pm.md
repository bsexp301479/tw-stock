## 四、風險與相依性

### 風險

1. **改收集器和 11/09～11/16 的第一次實戰重疊**：
   - 使用者每晚 `collect --catch-up` 用的是工作目錄的程式。PG 改到一半時若使用者收集，`alerts` 可能失敗。
   - 對策：
     - `catchup.py` 已用 `_guard` 個別包住 `alerts`，失敗只記在 `errors["alerts"]`，不影響借券、季報。
     - PG 每次存檔都保持 `alerts.py` 可匯入、可執行；動手前、回補前查 `collect_runs` 是否有進行中的收集。
     - QA 用 `git diff --stat` 確認 `twstock/collectors/` 下只有 `alerts.py` 有變動。
     - 若使用者某晚 `alerts` 失敗，PG 完成後使用者再跑一次 `collect --catch-up` 即可（`alerts_at` 沒更新，會自動重抓）。
2. **新來源的穩定性未知**：
   - 證交所網站的查詢頁可能有頻率限制、格式改版，或假日回傳空結果。
   - 對策：SA 在交易日收盤後實測；`fetch_alerts` 維持「任一端點格式不符就整批不寫」，避免半套資料；0 筆警告（F16-1 #5）。
3. **回補寫入錯誤的資料**：
   - 例如日期解析錯（民國／西元）、把權證寫進來，或把公告日寫成查詢日。
   - 對策：F16-1 驗收 #1（6213、2466、4526 反證）、#3（逐日筆數）、#6（既有列不變）；回補前先跑一次「只解析不寫入」（dry-run），把逐日筆數寫進 `04-dev.md`。
4. **重複**：舊 OpenAPI `notice` 若某天恢復提供資料，和新來源同一筆會重複。
   - 對策：`MERGE` 鍵是 (stock_id, alert_type, announce_date)，同一天同一檔只會有一列；`fetch_alerts` 已在寫入前去重。SA 要確認兩個來源的 `reason` 不同時保留哪一個。
5. **清單太長**：補上市後注意股可能 40～60 檔，總覽分頁變長。
   - 對策：注意組預設前 N 檔＋「顯示全部」；驗收 F16-3 #5（≤ 1.5 屏）。
6. **PG、QA 期間資料日變動**：基線與新匯出要連續執行，前後記 `collect_runs` 最大 `run_id` 與資料日，不同就重做基線。
